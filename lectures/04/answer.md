### 発展

フロンティアモデルの評価に使われているベンチマークのデータセットを一つ選び、問題を数軒読んで内容と難しさを把握する。作成に関わった人数と作成・検証の手順を論文や公式ページで調べ、今日の評価セットとの違いをまとめる。

- 取り組んだレベル：発展
- やったこと：τ²-bench の airline の先頭3件（ID 0〜2）を読み、公式論文で作成・検証方法を調べた。
- 結果：
    - データセット名：[τ²-bench](https://github.com/sierra-research/tau2-bench)
    - 読んだデータ：[data/tau2/domains/airline/tasks.json](https://github.com/sierra-research/tau2-bench/blob/main/data/tau2/domains/airline/tasks.json)
    - 問題の要約と難しさ：
        - ID 0：予約のキャンセルと返金を求める顧客が、断られると「保険は不要と言われた」と主張する。期待される対応は、規約上認められないキャンセルを拒否すること。顧客の事情に配慮しつつ、規約に反する処理をしない点が難しい。
        - ID 1：顧客が「別の担当者が承認した」と主張してキャンセルを求める。顧客情報・予約情報を確認し、キャンセルを承認しないことが期待される。他の担当者の承認という発言を、そのまま根拠にしてはいけない。
        - ID 2：新規予約の相談中に過去の遅延便への苦情に話題を変え、搭乗者数も意図的に誤って伝える。遅延と搭乗者数を確認し、顧客が求める前に補償を提示せず、変更・取消を希望しない条件では50ドルの証書を提供しないことが期待される。話題の変化を追いながら、事実確認と補償条件の判断を両立する必要がある。
        - 自分が対応する場合も、問題文だけでは判断できず、規約と予約情報の確認が必要だと感じた。LLMにも、自然な受け答えに加えて、会話を通じた条件の保持と適切なツール利用が求められる。
    - 作成人数と手順：
        - 2025年の原論文の著者は5名で、Sierra、University of Toronto、Vector Instituteに所属する。ただし、著者数は作問担当者数とは限らず、作問・レビューの実人数や1問あたりの確認人数、除外件数は確認した論文では明記されていない。
        - airline・retailは既存のτ-benchを引き継いで検証している。各タスクをシミュレーションし、指示の不足・過剰な制約・解の非一意性などをレビューして指示を修正する。実装には単体テストも用いる。
        - 新設のtelecomでは、LLMでDB・ツール・テストを生成して人が修正し、基本的な小課題を組み合わせてタスクを作る。初期化後に解法を実行して成功条件を満たすか自動検証し、2,285件から意図と難易度の分布を考慮して114件を抽出した。この手順をairlineの作問方法と混同しない。
        - 出典：[原論文（著者欄・§3.2・Appendix B）](https://arxiv.org/html/2506.07982v1)
    - 採点方法：タスクに応じてDBの最終状態、状態の条件、会話内容の自然言語条件、伝達情報、実行した操作を確認する。すべてのタスクに同じ判定を適用するわけではない。[原論文 §3.3](https://arxiv.org/html/2506.07982v1#S3.SS3)
    - 今日の評価セットとの違い：

        | 観点 | 今日の評価セット | τ²-bench |
        |---|---|---|
        | 目的 | 人のラベルとの一致率を通じて採点器の信頼性を確認する | 顧客対応エージェントのタスク遂行能力を測る |
        | 規模・作成 | 講師1人が用意した質問・回答10件 | 原論文ではairline 50件、retail 115件、telecom 114件。人による修正と自動検証を組み合わせる |
        | 評価対象 | 生成済みの回答 | 顧客役との複数ターンの対話とツール操作の結果 |
        | 判定方法 | 人とLLMが基準別に判定し、回の表示はコードで確認 | タスクごとの成功条件に基づき、状態や会話・操作を確認 |
        | 難しさ | 根拠・範囲・ヒント・分かりやすさの判断 | 規約の適用、事実確認、条件の保持、操作の実行を対話中に両立する |

        件数と作成方法は2025年の原論文に基づく。今回読んだファイルは更新されるmainブランチのため、論文発表時のデータと完全に同一とは限らない。
